## Summary

Crypto Trade is an event-driven research platform that ingests PumpPortal migration events and
collects time-stamped on-chain, market, holder, quote, risk, and alternative-data evidence for
each one. Built solo, May–July 2026.

## Context and constraints

Migration events fire in bursts and the source data comes from several independent feeds, so
the system had to handle concurrent writes, partial failures, and rate limits without losing
or duplicating records — a requirement for the data to be usable in downstream research at all.
Each captured event also needed a full evidence trail: on-chain state, live market quotes,
holder distribution, and risk signals, all time-stamped consistently enough to reconstruct what
was knowable about a token at the moment it migrated.

## Approach

Built a set of idempotent concurrent workers subscribed to PumpPortal migration events over
WebSockets, each writing its slice of evidence — on-chain token state, market price/liquidity
data, holder distribution snapshots, exchange quotes, and configurable risk-gate signals — into
per-event records keyed so re-processing the same event never produces a duplicate. A SQLite
WAL-based lifecycle tracker records each event's processing state (pending, in-flight per
worker, complete) so a crashed or restarted worker can resume mid-event instead of re-running
from scratch or silently dropping it. Configurable rate limits protect the upstream feeds from
bursty migration activity. Finished records are written as append-only, Zstandard-compressed
Parquet files, so every capture is both storage-efficient and auditable after the fact.

## Evaluation

Validated primarily by auditing captured records for completeness and consistency across
concurrent worker runs, rather than a formal benchmark — the goal was reliable data capture, not
a predictive model. The audit checked that every migration event produced a full set of
evidence fields, that concurrent workers never wrote duplicate or partially-overwritten records
for the same event, and that the lifecycle tracker's state matched what was actually present in
the Parquet output after worker restarts.

## Result

A working pipeline producing auditable, append-only, time-stamped evidence per migration event
for later research use.

## What changed

Idempotency and lifecycle tracking under concurrency needed more design work than the initial
data-collection logic — worth planning for up front on any similar event-driven ingestion
project.
